# Roadmap: Satya as an agent tool, and a verified public bug count

Two separate asks, with different risk profiles:

1. Expose Satya as a tool an LLM agent can call, instead of a config file a human hand-writes.
2. Get a real, defensible "found N bugs in M third-party apps" number, and eventually let
   people submit their own site to be tested.

This doc designs both and says which parts are safe to build now versus which need a consent
mechanism first.

## Where this starts from

Satya's verification core is already decoupled from how a flow gets specified:
`agent.loop.verify_action()` / `audit.middleware.VeritasAuditor` take a `BrowserAgent` and a
`do: Callable` (the action to perform) and don't care who wrote `do` — today it's generated by
`cli.build_do()` from hand-written YAML (`flows.example.yaml`), or passed directly from
`service/app.py`'s request body. Nothing about claim inference, backend diffing, or
reconciliation needs to change for either part below — they're a new way to *produce* a flow,
not a new way to *verify* one. See `docs/ARCHITECTURE.md` for the existing pipeline.

The one thing that does need to change for part 2: `allowed_domains` today is **self-declared**,
not verified. `service/app.py`'s `_prepare()` checks the target domain against a list the caller
put in the request body — it exists to stop an accidental prod run (e.g. a browser extension
firing on the wrong tab), not to stop a caller from typing in a domain they don't own. That
distinction matters once the caller isn't you anymore.

## Part 1 — MCP tool for agent-driven verification

### The problem it solves

`flows.example.yaml` requires a human to already know the app's selectors (`row_selector`,
`toast_selector`, CSS paths for every button). That doesn't scale past hand-curated demo apps
like TodoMVC. An agent that can read a page's DOM can supply that instead — the same way a
person would, just faster and without pre-writing YAML.

### Design: agent explores, Satya verifies

Two ways to split this; the second is a bigger project and should come later:

- **Option A (build this first): the calling agent decides what to click.** It reads the page
  (its own browser/vision tooling, or a `satya_inspect_page` primitive below), decides on a flow
  in plain terms ("click Delete on the second row"), and calls Satya to execute + verify it.
  Satya's reconciliation engine doesn't change at all.
- **Option B (later): Satya decides what to click.** A planner inside Satya looks at the DOM and
  proposes flows itself ("this looks like a CRUD list, try add/edit/delete"), so a caller can
  just say "test this site" with no flow authored at all. This is a materially bigger project —
  it's a small web-navigation agent sitting in front of the verifier — and should reuse whatever
  `inspect_page` returns rather than being designed from scratch.

Option A ships fast because it's a thin MCP wrapper around code that already exists.

### Proposed MCP surface

- **`satya_inspect_page(url, headless=true)`** — loads the page with the existing
  `BrowserAgent`/Playwright driver and returns a structural summary: interactive elements
  (buttons, inputs, links) with best-guess selectors, and candidate "row" containers (repeated
  sibling elements sharing a class or an id-like attribute, which is what `row_selector` /
  `id_attr` need). This is a new read-only method next to `BrowserAgent.act()` — it doesn't touch
  the reconciliation path.
- **`satya_run_flow(url, flow, ground_truth, backend_read_path?, selectors?)`** — wraps
  `VeritasAuditor` / `verify_action` directly. `flow` is the same action-list shape
  `cli.build_do()` already accepts (`fill`, `click`, `press`, `check`, `hover`, `dblclick`,
  `wait_for`, …), so an agent that called `inspect_page` first can fill this in itself. Returns
  verdicts + evidence; omit raw screenshots from the payload (report a path/URL instead) to keep
  responses small.
- **`satya_check_url(url, mode: "smoke" | "truthfulness")`** — thin wrapper matching the
  dashboard's existing two URL modes, for a one-shot check without authoring a flow by hand.

**Every call that can mutate (`run_flow` with a mutating action, `check_url(mode="truthfulness")`)
must check the target domain against a verified-domains store before running** — see Part 2. This
has to live inside the tool, not be left to the calling agent's judgment, exactly the way
`service/app.py` already refuses `allow_mutations` without `allowed_domains` today.

### What this does not require

No changes to `models.py`, `reconcile/`, or `agent/claim.py`. The verification oracle stays
exactly what it is; this only adds a new producer of `do` callables and a read-only page-scanning
primitive.

## Part 2 — a real "found N bugs" number, and a public submission flow

### Why arbitrary-URL mutation testing is not safe to ship today

Truthfulness checks perform real creates/edits/deletes. Running that against a site neither of
us owns, with no proof of permission, is the kind of thing that gets the service blocked, rate
limited, or into real legal trouble (unauthorized automated testing, ToS violations) — and
`allowed_domains` as it exists today is a self-reported list in the request body, not a
permission check. "Paste any URL and we'll test it" can only be safe for **smoke-check mode**
(already read-only, already the dashboard default, no change needed) until there's a real
ownership check in front of mutation mode.

### Ownership verification (same shape as Search Console / domain verification on most PaaS)

1. User submits a domain. The service generates a random token and offers two proof methods:
   - a `/.well-known/satya-verification.txt` file containing the token (works on any host, no
     DNS access needed), or
   - a DNS TXT record (`_satya-challenge.<domain>` = token) for people who'd rather not touch
     their web server.
2. User clicks "Verify." The service checks for either. On success, the domain is marked
   verified (method + timestamp) against the requesting account.
3. Re-verification on a schedule (e.g. before every truthfulness run, or every 30–90 days) —
   domain ownership changes, and a stale verification shouldn't stay trusted forever.
4. `service/app.py`'s domain check moves from "is this domain in the request body's
   `allowed_domains` list" to "is this domain verified for this account" — a DB-backed table
   instead of a client-supplied list. Smoke-check mode keeps working on any URL, unchanged.

### Where the first real bug-count numbers can honestly come from

- Keep extending the TodoMVC-style validation (`docs/VALIDATION.md`) — genuinely unmodified
  third-party code, no consent issue because nothing is mutated on a live third party's
  production system; this is how the Sammy.js and Lavaca findings happened. It's a real count of
  real bugs found, just not production traffic.
- An **opt-in verified beta**: once Part 2's verification flow exists, invite real site owners
  (starting with people who'd want this anyway — e.g. QA-minded teams) to verify a staging or
  sandbox domain and run truthfulness checks. Numbers from this phase are the first legitimate
  "found N real bugs in M real apps" data, because every one of them opted in.
- Any public "found N bugs" claim should go through a human triage pass before publishing —
  claim inference is tuned for CRUD-list UIs; broader site shapes (forms, checkout flows,
  dashboards) will produce more `NO_CLAIM`/inconclusive results until `inspect_page` generalizes
  past the row/id assumption documented in `docs/VALIDATION.md`'s Kendo/Lavaca findings, and an
  unreviewed inconclusive shouldn't get counted as a bug.

## Suggested sequencing

1. **MCP tool, Option A, against domains you already control** (your own repo's demo apps, plus
   any staging environment you have real access to). Proves the "agent supplies the flow"
   architecture without touching the consent question at all.
2. **Verified-domains store + verification handshake**, replacing the self-declared
   `allowed_domains` list in `service/app.py`. Prerequisite for anyone besides you to run
   mutation mode through the tool or the service.
3. **Opt-in beta** with real site owners on verified domains — this is where the first honest
   "found N bugs" number comes from.
4. **Public site / self-serve product** — smoke-check can be offered on any URL immediately;
   truthfulness checks stay gated behind verification. At this point also worth adding: rate
   limiting per domain (politeness — Playwright automation at volume can look like abuse to a
   target's WAF even with consent), a preview/dry-run mode so a submitter can see what Satya
   would do before it mutates anything, and Option B (Satya proposes its own flows) to cut the
   remaining friction of authoring one by hand.

## Open risk notes

- Mutation-mode runs can leave visible junk data (test todos, test orders) in the target app.
  Worth deciding whether runs attempt to undo their own actions afterward, or whether this is
  just a documented expectation for anyone who opts in.
- Claim-inference heuristics (toast text + DOM row-count delta) assume a CRUD list with a stable
  per-row id — exactly the assumption that failed on Kendo UI and Lavaca in
  `docs/VALIDATION.md`. Scaling past TodoMVC-shaped apps means `inspect_page` (or whatever Option
  B's planner becomes) has to get smarter about non-list UIs, not just more CSS selectors.
